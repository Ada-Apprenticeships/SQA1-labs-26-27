# Lab 2: Testing and regression tests

**Aim:** write tests that expose a defect before you fix it, then fix it through a branch and pull request.
**Time:** about 75 minutes.
**Assignment 1 criterion:** Testing.

## Why test first?

A test written **before** the fix should fail, proving it detects the defect. After the fix it should pass, and it stays in the suite as a **regression test** so the defect cannot quietly return. Your commit history then shows the sequence: failing test, then fix.

## 1. Start a branch

```bash
git switch main
git pull
git switch -c fix/overbooking
```

## 2. Look at the existing tests

Open `tests/test_bookings.py`. These were generated by an AI assistant. For each test, ask: **would this test fail if the feature were broken?** Most of them only check a status code, so they would pass even if bookings were badly wrong.

Also look at `tests/conftest.py`. The fixtures there give you an app with an empty in-memory database, a test `client`, users `alice` and `bob`, and an `event` with **capacity 5**.

## 3. Write a failing boundary test (worked example)

Defects cluster at boundaries, so test either side of the limit. Add this to the end of `tests/test_bookings.py`:

```python
@pytest.mark.parametrize("second_party, expected_total", [
    (1, 5),  # exactly fills the event: allowed
    (2, 4),  # one place too many: must be rejected
])
def test_bookings_cannot_exceed_capacity(client, alice, bob, event, second_party, expected_total):
    # event fixture has capacity 5: bob takes 4 places, then carol tries to book
    login(client, "bob")
    client.post(f"/events/{event.id}/book", data={"party_size": "4"})
    make_user("carol")
    login(client, "carol")
    client.post(f"/events/{event.id}/book", data={"party_size": str(second_party)})
    assert sum(b.party_size for b in Booking.query.all()) == expected_total
```

At the top of the file, add `import pytest` and change the conftest import to `from conftest import login, make_user`.

`parametrize` runs the same test with different inputs, which is ideal for boundaries. Using a second user keeps this test about capacity only, so it will not be affected by other rules such as one booking per user.

Run it:

```bash
uv run pytest tests/test_bookings.py
```

You should see `test_bookings_cannot_exceed_capacity[2-4]` **fail**: the app accepted a booking that should have been rejected. Good: the test detects the defect. Commit the failing test on its own:

```bash
git add tests/test_bookings.py
git commit -m "Add failing test for overbooking (#1)"
```

Replace `#1` with the number of your overbooking issue from Lab 1.

## 4. Fix the defect

In `app/bookings.py`, change:

```python

```

to:

```python
    if party_size > remaining:
```

Run the whole suite:

```bash

```

Everything should now pass. Commit the fix and reference the issue so GitHub links them:

```bash
git add app/bookings.py
git commit -m "Reject bookings that exceed capacity (fixes #1)"
git push -u origin fix/overbooking
```

## 5. Open a pull request

Open a pull request from `fix/overbooking` to `main` (GitHub shows a prompt after you push, or run `gh pr create`). In the description, say what changed and how you tested it, and include `Fixes #1`. Merge it, and the issue closes automatically.

## Extension: Behaviour Driven Development (optional, about 20 minutes)

**Behaviour Driven Development (BDD)** starts from behaviour described in plain language that a product owner, tester and developer can all agree on, before any code is written. Each behaviour is written as a **scenario** in the Given / When / Then form, known as Gherkin:

- **Given** the starting situation;
- **When** the action someone takes;
- **Then** the outcome that should follow.

The scenarios become the tests, so the requirements and the checks cannot drift apart.

### 1. Write the scenarios

Create a folder called `features` and a file `features/booking.feature`:

```gherkin
Feature: Booking places on an event
  As an attendee
  I want to book places on an event
  So that I have a guaranteed place

  Scenario: Booking the last remaining places
    Given an event with 5 places
    And 4 places are already booked
    When carol books 1 place
    Then the event is fully booked
    And carol has a booking for 1 place

  Scenario: Trying to book more places than remain
    Given an event with 5 places
    And 4 places are already booked
    When carol tries to book 2 places
    Then her booking is rejected
    And 4 places are still booked
```

Notice that this is requirement R2 in words a non-developer can check.

### 2. Turn each step into code

Create `tests/test_booking_behaviour.py`. Each step becomes a small, clearly named function, and each scenario becomes a test that reads like the scenario:

```python
"""Scenarios from features/booking.feature, written as Given / When / Then."""

from conftest import login, make_user

from app.models import Booking, User


def given_places_already_booked(client, event, places):
    login(client, "bob")
    client.post(f"/events/{event.id}/book", data={"party_size": str(places)})


def when_user_books(client, event, username, places):
    make_user(username)
    login(client, username)
    client.post(f"/events/{event.id}/book", data={"party_size": str(places)})


def places_booked(event):
    return sum(b.party_size for b in Booking.query.filter_by(event_id=event.id))


def bookings_for(username):
    user = User.query.filter_by(username=username).one()
    return Booking.query.filter_by(user_id=user.id).all()


def test_booking_the_last_remaining_places(client, alice, bob, event):
    # Given an event with 5 places
    assert event.capacity == 5
    # And 4 places are already booked
    given_places_already_booked(client, event, 4)
    # When carol books 1 place
    when_user_books(client, event, "carol", 1)
    # Then the event is fully booked
    assert places_booked(event) == event.capacity
    # And carol has a booking for 1 place
    assert [b.party_size for b in bookings_for("carol")] == [1]


def test_trying_to_book_more_places_than_remain(client, alice, bob, event):
    # Given an event with 5 places
    assert event.capacity == 5
    # And 4 places are already booked
    given_places_already_booked(client, event, 4)
    # When carol tries to book 2 places
    when_user_books(client, event, "carol", 2)
    # Then her booking is rejected
    assert bookings_for("carol") == []
    # And 4 places are still booked
    assert places_booked(event) == 4
```

Run it:

```bash
uv run pytest tests/test_booking_behaviour.py -v
```

If you have already merged your overbooking fix, both scenarios pass. To see the second scenario catch the defect, temporarily put `+ 1` back into the capacity check in `app/bookings.py`, run the tests again, then undo the change with `git checkout -- app/bookings.py`.

### 3. How this is done in industry

Here the scenarios and the tests are kept in step by hand. Tools such as **pytest-bdd** and **behave** run the `.feature` file directly, matching each Given / When / Then line to a Python function, so a scenario cannot be changed without its test changing too. We have not added one to this repository, to keep the dependencies (and the Lab 4 audit) unchanged, but the structure is exactly the same.
